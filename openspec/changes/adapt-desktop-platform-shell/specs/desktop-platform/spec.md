## Purpose

定义桌面应用在 macOS、Windows、Linux 上的窗口外壳、平台识别和构建交付契约，使统一的规划体验与各操作系统的窗口习惯并存。平台差异必须在构建与窗口边界收敛，不能改变业务数据含义，也不能用某一个系统的验证结果替代其他系统的发布证据。

## ADDED Requirements

### Requirement: 平台窗口装饰

系统 SHALL 在 macOS 使用原生红绿灯与融合式应用栏，在 Windows 使用与应用内容协调的单行融合标题栏及右侧窗口控件，在 Linux 使用桌面环境提供的窗口装饰。应用 MUST NOT 在 Windows/Linux 模拟 macOS 红绿灯或为其保留空槽，也 MUST NOT 覆盖用户的 Linux 窗口按钮顺序与位置偏好。

#### Scenario: macOS 常规窗口
- **WHEN** 用户打开 macOS 原生应用
- **THEN** 原生关闭、最小化、全屏按钮位于应用栏左侧专属安全区，应用按钮与系统控制不重叠
- **AND** 应用栏与当前白底或灰底画布协调，不出现第二条重复的应用标题栏

#### Scenario: Windows 常规窗口
- **WHEN** 用户打开 Windows 原生应用
- **THEN** 顶部只有一行融合工具栏，右侧以 Windows 熟悉的顺序提供最小化、最大化/还原、关闭控件，背景与当前主题连续
- **AND** 左侧不保留 macOS 红绿灯区域；窗口控制与应用操作分区明确，没有第二条系统标题栏或第二套控制按钮

#### Scenario: Linux 桌面偏好
- **WHEN** 用户在 GNOME 或 KDE 的受支持桌面会话中打开应用，或改变窗口装饰按钮的可用布局
- **THEN** 系统窗口装饰遵从桌面环境；应用内部控件位置稳定且不与其重叠
- **AND** 应用不要求所有 Linux 桌面使用固定高度或固定左右顺序的窗口控制

### Requirement: 原生窗口交互保持完整

系统 SHALL 保留各平台提供的拖拽、缩放、最小化、最大化/还原、关闭和可用的窗口排列交互。Windows 自定义外壳 SHALL 提供系统可识别的窗口控制与原生菜单行为，而非只复现按钮点击外观。应用功能按钮 MUST NOT 触发窗口拖拽；关闭行为 SHALL 进入既有退出流程，MUST NOT 因平台适配新增托盘驻留或自动确认 Coach 预览。

#### Scenario: Windows 窗口排列
- **WHEN** 用户在启用了窗口排列功能的 Windows 11 上拖动标题栏空白到屏幕边缘，或悬停融合栏中的最大化/还原按钮
- **THEN** 系统的贴靠与原生布局选择仍可使用；应用不用自绘弹层冒充系统布局菜单
- **AND** 选择能容纳应用最小尺寸的分区后正确贴靠，正文与窗口控制均可操作

#### Scenario: Windows 系统菜单与操作隔离
- **WHEN** 用户右击标题栏空白或按下 `Alt+Space`，随后通过菜单调整窗口
- **THEN** 显示并执行原生系统窗口菜单；双击空白可最大化/还原，点击应用按钮或窗口控制不被识别为空白双击

#### Scenario: Windows 单次窗口操作
- **WHEN** 用户点击最大化/还原或关闭按钮，或者在 Windows 系统菜单执行相同动作
- **THEN** 每次操作只执行一次，图标随实际窗口状态更新；关闭经过既有生命周期处理，不强杀进程或绕过持久化

#### Scenario: Linux 拖拽与系统菜单
- **WHEN** 用户通过桌面环境支持的标题栏拖拽、双击或系统窗口菜单调整窗口
- **THEN** 对应操作遵从桌面环境，恢复窗口后应用内容和面板仍可操作

#### Scenario: macOS 拖拽与控制隔离
- **WHEN** 用户拖动应用栏明确的空白区域，或操作原生红绿灯
- **THEN** 窗口响应原生操作；点击 Later、页面标签、Coach、Issues 或设置只触发该控件功能

#### Scenario: 关闭和重开
- **WHEN** 用户从同平台的系统关闭入口关闭应用，再次打开
- **THEN** 已保存计划和待确认改动按既有持久化契约恢复，不因窗口适配被丢弃、自动确认或自动拒绝

### Requirement: 窗口状态与安全区同步

系统 SHALL 在启动、最大化、还原、全屏进入/退出、跨显示器移动后保持系统控制、应用工具栏和内容区可见可用。系统控制的安全区 SHALL 随实际窗口状态调整，MUST NOT 因动画、旧尺寸或旧缩放比例产生按钮重叠、持续空白或整窗错位。

#### Scenario: macOS 全屏往返
- **WHEN** 用户进入全屏且系统控制不再占用应用栏，随后退出全屏
- **THEN** 全屏时不留下常规窗口的整块红绿灯空槽；退出后在系统按钮重新占用该位置前恢复安全区
- **AND** 系统全屏标题栏临时显现时不遮挡可操作的应用按钮

#### Scenario: 跨显示器缩放
- **WHEN** 用户在不同缩放比例的显示器之间移动窗口，随后最大化和还原
- **THEN** 工具栏、弹窗和侧栏使用新的可用客户区尺寸，任务光标及浮层锚点保持正确，窗口不需要重启才能恢复显示

#### Scenario: 失去焦点
- **WHEN** 窗口失去焦点后重新激活
- **THEN** 系统控制遵从原生激活态，应用正文保持可读，输入、选中计划和未完成草稿保持原状

### Requirement: Windows 融合窗口栏的可用性

系统 SHALL 使自定义窗口控制具备可辨识图标、可访问名称、悬停/按下/键盘焦点及失焦状态。窗口控件 SHALL 固定在右端，命中范围随 DPI、最大化与布局变化保持同步。自定义外壳初始化失败时，系统 MUST 恢复可操作的系统窗口装饰并记录故障，不能留下无法移动或关闭的无边框窗口；此降级不能代替正常方案验收。

#### Scenario: 窗口按钮与业务按钮区分
- **WHEN** 用户在任一主题下移动指针经过设置与窗口控制
- **THEN** 两组控件具有明确间隔，关闭按钮仅在交互态使用危险色，普通状态与整体浅色风格协调
- **AND** 窗口控制不使用任务颜色条、胶囊选中态或 macOS 彩色圆点来表示功能

#### Scenario: 键盘与辅助技术
- **WHEN** 用户用键盘或屏幕阅读器访问最小化、最大化/还原和关闭控件
- **THEN** 可以识别当前动作并执行，焦点清楚可见，状态变化后名称正确；系统高对比度模式下控件仍可辨认

#### Scenario: 缩放后的命中区域
- **WHEN** 用户把窗口移动到另一 DPI 显示器并最大化、还原
- **THEN** 按钮可见范围与实际点击和 Snap 触发范围一致，不出现图标能点而边缘失效、触发相邻按钮或不可见热区

#### Scenario: 外壳初始化失败
- **WHEN** 自定义外壳无法建立可靠的窗口控制和命中区域
- **THEN** 显示可移动、可缩放、可关闭的系统装饰及普通应用工具栏；自定义控制不重复显示，失败可从诊断日志识别，本地计划继续可用

### Requirement: 目标平台从构建到界面一致

系统 SHALL 以明确的目标平台生成原生应用，窗口外壳、前端平台提示、原生能力与安装产物 MUST 指向同一目标。目标平台 MUST NOT 由用户主题、浏览器用户代理、运行机器名称或可编辑设置覆盖；缺失或不支持的原生目标 SHALL 阻止打包并给出可诊断错误。

#### Scenario: 构建机与目标不同
- **WHEN** 构建工作在另一种主机架构上进行，或在 macOS 生成通用架构安装包
- **THEN** 安装产物与嵌入的前端仍采用目标平台的外壳和快捷键规则，不误用构建主机或浏览器的外壳

#### Scenario: 浏览器预览
- **WHEN** 开发者单独打开 Web 预览而没有原生窗口
- **THEN** 界面使用普通应用工具栏，无红绿灯空槽、虚假的系统窗口按钮或原生拖拽请求
- **AND** 预览可以按浏览器所在系统显示键盘提示，但不能据此声明某原生平台已通过测试

#### Scenario: 目标配置不一致
- **WHEN** 原生目标缺失、不受支持，或打包试图复用另一平台的前端产物
- **THEN** 构建验证失败，明确报告目标不一致，不输出可被误认为有效的分发包

### Requirement: 原生编译能力按目标隔离

系统 SHALL 使每个桌面目标只要求该目标需要的原生能力与 SDK。平台差异 MUST 在编译边界隔离，不能只依赖界面隐藏或运行时分支；三个平台 SHALL 共享相同的计划、日期、预览确认与存储语义。

#### Scenario: 独立工具链构建
- **WHEN** 开发者在具备对应平台前置依赖的干净环境中构建 Windows 或 Linux 目标
- **THEN** 不需要安装 Apple SDK 或链接 Apple 专属框架；macOS 构建也不要求 Windows SDK 或 Linux 桌面开发库

#### Scenario: 凭据后端选择
- **WHEN** 三平台应用分别保存并在重启后读取 BYOK 凭据
- **THEN** 各自使用对应系统的持久化安全凭据服务；真实分发构建不能静默使用测试用内存凭据服务

#### Scenario: Linux 凭据服务不可用
- **WHEN** Linux 会话没有可用的安全凭据服务，或服务被锁定且无法完成访问
- **THEN** AI 配置或调用给出可理解的错误，本地计划继续可用；不得把密钥回退保存到明文配置

### Requirement: 按目标交付安装产物

系统 SHALL 为 macOS、Windows 和 Linux 分别提供 amd64 与 arm64 两个架构的独立产物：macOS 应用/磁盘映像、Windows 安装程序、Linux AppImage 和 Debian 安装包。不同目标的构建输出、缓存和校验证据 SHALL 可区分；同一版本的产品名、应用标识与版本信息 SHALL 一致。

#### Scenario: 独立生成安装包
- **WHEN** 开发者执行某个目标的完整分发构建
- **THEN** 只产出该目标声明的格式，包含正确图标及必要运行依赖，不把 macOS 包作为 Windows/Linux 的构建结果

#### Scenario: 前端缓存复用
- **WHEN** 同一工作区或持续集成任务先后构建不同平台
- **THEN** 每次重新生成或验证当前目标的前端资源；上一目标的外壳、快捷键或产物不能混入当前安装包

#### Scenario: 构建与正式发布分开
- **WHEN** 构建验证流水线完成
- **THEN** 保存各目标安装包与日志，未执行正式发布的产物不被标记为已发布；本变更不自动推送版本标签、发布公开版本或上传签名密钥

### Requirement: 跨平台验收证据分层

系统的交付记录 SHALL 区分文档就绪、配置校验、原生编译、安装启动、真实窗口交互和签名发布状态。每个声明支持的平台 SHALL 有自己的安装与窗口交互证据；缺少环境的项目 MUST 明确标注未验证，不能用浏览器模拟或另一平台结果代替。

#### Scenario: 只有 macOS 可测试
- **WHEN** 当前执行环境只能运行 macOS 应用
- **THEN** 可以记录 macOS 实测和其他目标的静态/组件验证，Windows/Linux 的原生安装、窗口控制和 DPI 验收仍保持未验证

#### Scenario: 三平台发布候选
- **WHEN** 团队准备把某版本标记为三平台发布候选
- **THEN** 分别具备对应平台的安装、启动、窗口控制、键盘操作、双主题及缩放证据，并单独列出尚未完成的签名或最低系统版本认证


### Requirement: 跨平台共享选择器与浮层

应用内的语言、周起始日、诊断等级、供应商模型及 API 格式选择 SHALL 使用同一应用内选择组件。菜单 SHALL 对齐触发框并避让客户区边缘，不依赖操作系统原生 select 的覆盖定位；系统文件和权限对话框仍使用原生能力。

#### Scenario: 选择框在窗口边缘展开
- **WHEN** 用户在任一平台打开语言或周起始日选择框，或缩小窗口
- **THEN** 菜单默认位于触发框下方，对齐其边缘；空间不足时翻转或限制高度并滚动，选中标记与标签不遮挡触发框

#### Scenario: 键盘与内层关闭
- **WHEN** 用户使用方向键、文字搜索、Enter 或 Escape 操作选择器
- **THEN** 可选项可达、禁用项不可提交；Escape 仅关闭选择器并把焦点还给触发框，不同时关闭设置

#### Scenario: 浮层表单保留原生编辑行为
- **WHEN** 用户在专注块排期浮层的时间或时长输入框按方向键、Home 或 End
- **THEN** 按键留给输入框；仅菜单项使用菜单导航逻辑，表单浮层具有表单对话框语义且不会吞掉输入操作

### Requirement: 用户路径与平台服务边界

应用 SHALL 通过系统目录解析、Path/PathBuf 或 path.join 构造运行路径，保持用户目录、应用数据目录和可编辑 AI 指令目录的职责分离。平台特有凭据、通知和窗口能力 SHALL 由适配边界承担，不复制业务服务或拼接平台专属 shell 命令。

#### Scenario: Windows 非 ASCII 与空格目录
- **WHEN** 用户的系统目录包含空格或中文，并保存供应商配置、persona、SKILL 或日志
- **THEN** 应用在解析后的用户目录中正常读写，不写入源码目录或硬编码用户目录；进程参数保留完整路径，更新失败不损坏原配置

#### Scenario: 系统能力不可用
- **WHEN** 目标平台的凭据或通知服务不可用
- **THEN** 能力边界返回明确状态或错误，本地计划继续可用，不切换到明文凭据或伪报通知成功


### Requirement: UI 运行时能力基线

发布配置 SHALL 声明能够支持共享 UI 依赖的最低运行时，而不是仅使用 Tauri 可启动的最低系统版本。v0.1.1 的 macOS 最低版本为 13.3，Windows WebView2 最低版本为 111；Vite 使用 Safari 16.4、Chrome 111 与 Firefox 128 的编译目标。

#### Scenario: Windows 旧 WebView2
- **WHEN** 安装器检测到已安装 WebView2 低于声明的版本
- **THEN** 安装器按 Tauri 的更新策略尝试更新运行时；未完成更新的环境不能被声明已通过 GUI 验收

#### Scenario: Linux 引擎认证
- **WHEN** Linux 发行版具有 WebKitGTK 4.1 ABI
- **THEN** 仍须核对具体引擎版本、系统依赖和桌面会话，不以 ABI 名称直接宣称 UI 兼容
