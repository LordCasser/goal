## Context

现有 `ProviderConfig.extra_headers` 保存非敏感键值，但没有 UI 和传输调用。`Credentials` 已隔离系统凭据机制；`test_and_save_provider` 在互斥锁下测试草稿后提交；真实请求统一经 `ResolvedProvider` 和 `sampling::sample`。

## Goals / Non-Goals

**Goals:** 接通完整最小闭环，复用供应商配置、凭据适配器和统一采样入口；认证和路由 Header 均可配置。

**Non-Goals:** 不做每模型覆盖、Header 模板、任意代理配置、凭据架构重构或新版本发布。

## Decisions

1. 配置中的 `extra_headers` 改为名称数组；`save_provider` 额外接收 `header_values: Map<string,string>`，仅承载这次填写的新值。既有同名值从凭据存储合并；名称统一为小写，新增缺值拒绝。避免使用带值的通用配置对象在普通查询、日志或 Coach 中泄漏。
2. 所有值保存为单个供应商 Header JSON 凭据（独立于 API Key），沿用 `Credentials` 的平台封装；无 Header 时不访问该凭据。比让用户判断每一项是否敏感更简单。API Key 行的移除行为不隐式删除独立 Header。
3. 保存采用既有测试后提交模式，扩展凭据写入失败和配置落盘失败的回滚。测试失败不写任何状态，返回值仅有 Header 名称；已保存连接重测/解析若凭据缺失必须报错，不静默少发。
4. `ResolvedProvider` 和 `SamplingRequest` 携带运行时 Header 键值对；客户端集中校验并以 `HeaderMap::insert` 覆盖默认 Header。先设置默认 JSON/SSE/auth，再应用自定义项；传输层保留名单由统一 Header 模块定义。所有值注册脱敏，错误返回同步脱敏。
5. 表单在 API 格式与模型之间提供“请求 Header（可选）”和“添加”入口，无条目时不展示空表格。添加后名称自动聚焦；名称/值/删除在宽面板同行，窄宽度自动换行。值默认隐藏，当前输入可显示/隐藏；保存后清空草稿、显示“已保存，留空保留”。行内错误通过 `aria-describedby` 关联。名称更改后需填写新值。
6. 供应商导航使用按内容高度排列的轻量列表，不跟随表单拉长。添加入口移到管理区标题旁，空列表不占侧栏；窄窗口把列表移至表单上方，保留编辑与激活选择的分离。

## Risks / Trade-offs

- 已保存值不回显，修改需要重新输入 → 行内明确“留空保留”，允许单独删除，名称变更时提示填写值。
- 凭据和配置不是同一事务 → 在供应商写锁下保留旧值并在失败时回滚；错误明确报告，不假装保存成功。
- 系统凭据存储需要平台支持 → 复用既有跨平台实现，不增加平台分支。
- 旧隐藏字段原为键值数组 → 当前没有面向用户的编辑入口，本次不新增兼容层；上线前确认真实配置未使用旧非空字段。
