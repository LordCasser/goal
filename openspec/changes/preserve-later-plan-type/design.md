## Context

当前 Later 是固定 id 为 `later` 的收纳周期，任务移动会带走同周期后代，但任务本身没有记录“准备安排到哪一层”的意图；`promote_later_goal` 直接把调用方给出的周期 id 交给通用移动逻辑。现有日历领域已经以本地日期和 `week_start_day` 计算周/日身份，并提供周期日历键的唯一约束。相关背景与行为边界见 `proposal.md` 及本 change 的三个 delta spec。

实现需要继续遵守数据库为唯一真相源、日期使用本地日期字符串、Rust 事件只做缓存失效通知的约束。Later 仍是一个周期容器，不新增独立实体，也不恢复关系历史。

## Goals / Non-Goals

**Goals:**

- 让 Later 任务在数据、IPC 和界面上带有可验证的 `month` / `week` / `day` 计划类型。
- 让通用移动和 Later 提升共用同一套事务边界，保证子树、父关联、类型清理和周期创建一起提交或一起回滚。
- 让周、日提升由后端按当前本地日期决定唯一目标周期；已有周期复用，缺失周期在同一事务内创建。
- 保持长期提升的单候选直接执行、多候选选择行为，并为周/日提供明确的行内状态与错误反馈。

**Non-Goals:**

- 不改变普通非 Later 跨周期移动的既有关系策略；本 change 只在移入/移出 Later 的路径上维护类型和无效外部父关联。
- 不创建按计划类型拆分的 Later 容器，不改变 Later 的固定周期 id。
- 不记录父关系历史、恢复被解除的历史关联或重建过去的周期来源。
- 不改变周期完成、删除、长期时长或任务完成语义。

## Decisions

### 1. 在统一任务行上增加可空类型字段

在 `tasks` 的持久化与 Rust/TypeScript `Task` 结构中增加 `later_plan_type`，允许值为 `month`、`week`、`day` 或 `NULL`。数据库用值域约束和针对 `cycle_id = 'later'` 的写入/更新约束保证：Later 外的行只能是 `NULL`，Later 内的非空值只能是三个合法类型。迁移不猜测旧数据的来源，旧 `NULL` 在展示和提升时按 `month` 解释；新建 Later 想法直接写入 `month`。

选择 nullable 字段而不是单独的 Later 表，是因为任务树、提案快照、删除级联、编辑工作区和现有事件都以统一任务行为为边界。单独实体会复制任务关系并引入跨表同步真相源。

### 2. 以事务内共享移动 helper 统一状态变化

抽出一个只接受已打开事务的移动内核，由普通任务移动和 Later 提升调用。内核负责校验源/目标可编辑性、移动同周期子树、计算目标位置、更新 `later_plan_type`，以及收集需要失效的源/目标周期。移入 Later 时按移动前源周期类型给整个同周期子树赋值；移出 Later 时清空该字段。

Later 是共享容器，因此不能按 Later 容器的树把不同类型的项合并。只有同一源周期内随根任务移动的同周期后代才作为子树一起移动；周项与其分别移入的长期目标仍按各自类型作为独立 Later 项。已有合法跨层级 `parent_id` 保留。

移出 Later 时只检查此次移动根任务的外部 `parent_id`（父项不在本次同周期子树内）：父项若仍在 Later，或父子周期对目标不再满足同周期/相邻层级规则，则清空该关联；同周期子树内部的父关系不重复检查，合法相邻层级关联保留。该判断在已知最终目标周期后、更新移动行前完成，避免以移动中的中间状态判断。

不在 Later 的普通移动继续走原有关系逻辑，避免把本 change 扩展为全局关系迁移。

### 3. 让提升入口只把长期选择交给前端

将 `promote_later_goal` 的 `target_cycle_id` 改为可选：

- `later_plan_type = month`（含旧 `NULL`）时，保留当前行为：一个可用长期周期直接移动，多个由界面选择后传入 id；后端校验传入周期确为可变的长期周期。
- `later_plan_type = week` 且未传目标时，后端读取 `week_start_day`，用当前本地日期计算周首日，按唯一日历键复用或创建周周期。
- `later_plan_type = day` 且未传目标时，后端使用当前本地日期，按日历键复用或创建日周期；需要的周父容器也在同一事务内复用或创建。

周/日目标解析只在后端发生，前端不传日期、不按设备时区计算周期。周期唯一键与数据库约束共同防止并发或重复点击创建重复周期；创建、移动、父关联整理和类型清理全部成功后才提交。

### 4. 保持 Later 行的轻量反馈

工作台沿用当前 Later 行、弹出菜单和 React Query 失效机制。行根据 `later_plan_type` 显示静态小字“长期目标 / 周计划 / 日计划”，按钮文案分别为“安排到长期周期 / 安排到本周 / 安排到今天”。周/日按钮直接调用可选目标参数为空的 IPC；长期按钮沿用单候选直达、多候选菜单。请求中的按钮禁用，失败消息绑定到当前行并保留编辑状态；成功只刷新源/目标工作区和周期状态，不增加 toast 或新视觉层。

### 5. 迁移与兼容策略

新增一次前向数据库迁移和对应回读/写入字段。现有 Later `NULL` 数据不批量回填为猜测的历史值；查询仍返回 `NULL`，消费端在展示和提升决策时按长期语义解释，标题编辑不会因为缺少元数据而自动补值，只有新建或再次移入 Later 才写入明确类型。前端 IPC 类型与测试 fixture 同步字段，事件载荷仍只包含已有失效范围，不携带业务快照。

## Risks / Trade-offs

- [旧 Later 项无法还原来源] → 将 `NULL` 明确按长期处理并保持原数据，界面不声称知道历史来源。
- [创建周/日与移动跨多张表] → 所有步骤在同一个 SQLite 事务内完成，并依赖日历键唯一约束；任一步骤失败回滚整个操作。
- [父关系可能跨 Later 类型] → 只在离开 Later 时按最终周期重新校验外部父项；仍在 Later 或不满足相邻层级的关系清空，合法关系保留。
- [快速重复点击] → 前端锁定进行中的行，后端在事务中重新读取任务和目标；任务已移动或目标已存在时返回当前状态/稳定错误，不重复创建周期。
- [共享移动 helper 扩大影响面] → 保持普通非 Later 移动的关系分支不变，只把 Later 类型赋值、清理与移出关系校验置于 Later 条件内，并用回归测试覆盖旧移动路径。

## Migration Plan

1. 发布数据库迁移与任务读写字段，使旧数据库可读取 `NULL` 并继续显示；迁移失败时不改动原任务数据。
2. 发布后端事务移动与提升逻辑，再接入可选 `target_cycle_id` 的 IPC。
3. 发布 Later 行类型、按钮和行内错误状态，成功后按已有事件刷新缓存。
4. 验证迁移数据库、空的周/日容器、已有目标周期、结束周期、重复请求、子树及跨层级父关联后再作为完成版本分发。
