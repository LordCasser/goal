## Context

见 `proposal.md`。现有 `month` 周期创建服务将 `ends_on` 与 `duration` 视为必填，并在未传 `progress_check` 时写入半程检查。`cycles.progress_check` 的列级 CHECK 又要求存在结束日。工作台默认周期、范围查询和列头也假设长周期总有结束日。

## Goals / Non-Goals

**Goals:** 保持一张 `cycles` 表和现有 `ProgressCheck` 类型；以可空的 `ends_on`、`duration`、`progress_check` 表达开放式周期和无检查，完成四种组合。日期仍按本地日字符串运算。已有有期限周期及其检查安排保持原值。

**Non-Goals:** 不增加新的周期类型；不替用户自动决定何时结束开放式周期；不把进度检查改造成系统通知或重复提醒服务。

## Decisions

1. **开放式日期身份**：`starts_on` 必填，`ends_on` 与 `duration` 同时为空，`calendar_key` 使用 `long-term:{starts_on}:open`。同一天只允许一个开放式长期周期，与有期限周期的键互不冲突。保持现有唯一索引，不新增身份列。
2. **检查安排为空即明确不检查**：新建周期仅保存用户显式选中的 `ProgressCheck`；不再把空值推导为半程检查。已有周期的持久化检查记录不变。工作台移除读取时的半程回退，以免把用户的“无检查”重新解释为默认检查。
3. **放宽原列约束**：新增迁移先复制 `progress_check` 到新列，再删除旧列并重命名新列。新 CHECK 仍要求检查只属于有效长期周期；一次检查在有结束日时受上界限制，无结束日时只受开始日限制；定期间隔为正整数。迁移在既有逐版本事务内完成，不改已应用 SQL 的校验和。
4. **创建服务负责组合校验**：预设、自定义、有开始日无结束日三种输入互斥。开放式周期仍可进入生命周期，其他无时长周期继续被拒。AI 提议使用同一服务，并同步允许开放式输入组合。
5. **预览和选择**：前端时间线对开放式周期只取有限个近期检查日期，不计算无穷总数；有期限但无检查只显示开始与结束。工作台选择与范围查询将 `ends_on = NULL` 视作无上界，已完成状态仍按生命周期判断。

## Risks / Trade-offs

- **列级约束迁移失败** → 在空库与含既有检查数据的库上测试迁移和读回；失败时事务回滚，原表保留。
- **无期限重复检查的预览无界** → 仅生成固定数量的近期日期，不遍历无限时间。
- **旧代码把 `NULL` 当成默认半程检查** → 清点并移除工作台与创建服务的隐式回退，同时覆盖四种组合测试。
- **开放式周期匹配过多日期** → 范围查询只返回开始日不晚于查询末日的周期，完成与归档继续由调用方筛选。

## Migration Plan

追加一个 schema 迁移，保留现有行和既有检查 JSON。新版本启动时一次性执行；若任一步失败，迁移事务回滚，应用不带着半迁移状态启动。无需改写用户现有周期的日期。
